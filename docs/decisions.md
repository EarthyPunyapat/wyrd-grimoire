# Decision log

Every design decision behind this spec, in the order it was made, with the reason. These came out of a structured design interview with the owner on 28 October 2026. **Treat them as settled.** If implementation reveals a real problem with one, raise it with the owner rather than quietly changing course.

## Foundations

| # | Decision | Why |
|---|---|---|
| D1 | **Purpose: a game the owner actually plays.** Not a learning exercise, not a product. | Optimise for fun and depth of play, not for teaching or for monetisation. |
| D2 | **Build an engine**, not a single hard-coded game. | The owner wants to play many campaigns in many genres. |
| D3 | **Hybrid truth model.** Code owns hard state (HP, items, location, quests, dice). The model may *propose* changes through validated tool calls and has free rein over flavour (description, dialogue, personality). | Pure "model as GM" drifts: forgets inventory, lets the player talk past any obstacle, no stakes. Rule of thumb: if it can kill you or you can lose it, code owns it. |
| D4 | **Heavy crunch.** CRPG-weight rules. | Owner preference. |
| D5 | **Solo** for v1; party stored as a list so multiplayer stays possible. | Multiplayer is a project of its own (turn order, spotlight, concurrency). |
| D6 | **Full engine, no fixed time budget.** | Owner wants a complete app; build it milestone by milestone. |

## Rules

| # | Decision | Why |
|---|---|---|
| D7 | **Universal core in code + genre packs as data + code plugins** for subsystems data can't express. | "Any genre" rules out one genre-specific ruleset; fully data-driven rules turn into writing a programming language. |
| D8 | **Any genre; fantasy is the first pack.** | Models know fantasy deeply; it is the best first test of the engine. |
| D9 | **Free text → model parses into structured actions → engine validates → model asks to clarify** (with numbered options) when ambiguous or illegal. Valid actions shown as hints in combat. | Feels like a human GM while keeping the rules honest. |
| D10 | **Zones and range bands**, not a grid. | Grids are painful in text and models are unreliable at spatial reasoning. |
| D11 | **Dice system is a per-campaign option: d100 roll-under (default) or d20 + modifier.** Both return the same four degrees of success; skills are stored on one 0–100 scale. | Owner likes d100 and d20. The engine only consumes degrees, so the dice module is swappable. |
| D12 | **Progression is a per-campaign option: classless (default), use-based, hybrid, classes.** Genre packs supply archetype templates. | Owner wanted all of them. Classless and use-based work in any genre for free; classes need per-pack content. |
| D13 | **Show the math: a toggle, on by default.** A mechanics log sits under the narration. | Crunch only feels fair when visible; it also exposes narration that disagrees with the dice. |
| D14 | **Defeat, not death, by default.** 0 HP / lethal wound → captured, robbed, left for dead, rescued — with lasting consequences. **Hardcore mode = permadeath.** | Failure that creates story beats a game-over screen; hardcore exists for real stakes. |
| D15 | **What locks when:** dice and progression lock at creation; difficulty, math display and subsystem toggles change any time; hardcore is chosen at creation and can be turned off (save permanently marked softcore) but never turned back on. | Switching dice mid-run means rescaling the sheet; hardcore must not be switchable after a lucky streak. |
| D16 | **Health = HP + wounds.** HP is stamina/near-misses; big hits or 0 HP cause wounds at body locations. **"Realistic":** hit locations, armour coverage per location, bleeding, fractures, infection, healing over days and weeks. | Owner wants realism; HP keeps combat readable, wounds create lasting consequences. |
| D17 | **Lethality: gritty + Luck.** Everyone uses the same deadly rules; a small Luck pool can reroll a check or downgrade a lethal wound. Lethality is a campaign dial. | Realistic danger without one bad roll ending a 50-hour campaign. |
| D18 | **Combat turns: 3 action points per turn, rolled initiative.** | Cleanest fit for free text: "kick the table, duck behind it, shoot" = three actions. |
| D19 | **Full companions**, up to 3: own sheets, combat turns, opinions, loyalty, can leave. Per-companion toggle: AI-controlled or player-controlled. | Makes solo CRPG play feel alive. |
| D20 | **Every subsystem is built and every subsystem is toggleable**, with presets: Story / Standard / Simulation / Custom. | Owner wants to track everything but not always. |

## World and story

| # | Decision | Why |
|---|---|---|
| D21 | **Worlds come from three sources:** generated at campaign start from a pitch, generated lazily as the player explores, or loaded from hand-written packs. | Flexibility; generated worlds for variety, packs for authored settings. |
| D22 | **Nothing exists until it is written into state; once written, it is canon.** The model reads canon, never its own earlier prose. | Prevents the classic drift (the shopkeeper's name changing between visits). |
| D23 | **Story mode option: Threat Clock (default) or Living World.** Threat Clock = a main threat that advances if ignored, with side hooks. Living World = no doom clock; the world simulates daily life and the player just lives in it. | Direction without railroading, plus a chill mode. |
| D24 | **Character creation: all three paths** — session-zero interview (main path; writes backstory hooks into canon), form/wizard, quick-start pregens — sharing one sheet editor. | Each suits a different mood. |
| D25 | **Content dials per campaign**: violence, horror, romance (off / fade-to-black), language, plus lines and veils. | Standard tabletop safety tools. Cloud providers' own policies still apply on top. |

## Memory

| # | Decision | Why |
|---|---|---|
| D26 | **The full memory system:** event log as source of truth; canon graph with provenance; memory pyramid (turns → scenes → chapters → arcs); NPC minds with rumour propagation; context assembler with exact lookup + graph neighbours + semantic retrieval; canon guard; player-facing journal/codex with retcon. | The owner asked for an intricate system capable of very long campaigns. It is the heart of the engine. |
| D27 | **Contradictions:** the canon guard regenerates narration once silently; if it still conflicts, it flags it to the player. **Rewind:** unlimited (disabled in hardcore). **Reroll narration** button: same outcome, new prose; dice never change. | Owner delegated; these are the best options. |

## Derived decisions (made while writing the spec)

| # | Decision | Why |
|---|---|---|
| D37 | d20 conversion: `modifier = round((skill − 50) / 5)`, Normal DC 11. A skill of *s*% has the same base success chance in both systems. Difficulty steps are ±20% (d100) = ±4 DC (d20). | Keeps the two dice modules balanced against each other so packs don't need per-system numbers. |
| D38 | Canon guard runs **before** narration is shown by default (narration is buffered; mechanics log and a typing indicator appear immediately). A setting allows "show first, check after". | D26 requires contradictions to be caught before the player sees them; the setting exists for players who prefer instant streaming. |
| D39 | Enemy and companion tactics use a **deterministic utility AI** in the engine; the model only writes their spoken lines. | Keeps combat fair, fast, cheap and replayable. |
| D40 | Narrator output uses light markup (`<say who="…">`) for dialogue so TTS can voice each NPC differently. | Per-NPC voices (D32). |

## Implementation decisions (M1)

| # | Decision | Why |
|---|---|---|
| D41 | The dev CLI lives in **`apps/cli`** (`bun run wyrd`). | M1 needs a CLI before the server exists, and it is an app, not a library. |
| D42 | **`storage` takes the engine's `reduce` as a parameter** instead of importing `engine`; its SQL projections are built from event payloads. | Keeps the spec's dependency rule (`core ← storage`) while still letting storage keep snapshots and replay in one transaction. |
| D43 | **`CheckRequest.tags`** (sight, hearing, attack, escape, resist, fear…) added. | Conditions need to know what kind of check it is (Blinded fails sight checks, Unconscious allows only resistance, Grappled spares escapes). |
| D44 | **`GameState.lastChecks`** keeps each actor's latest check; push and Luck act on it. `CheckResolved` records both the roll (`result`) and what counts (`effective`), plus `attempt` = initial / push / luck. | Push and Luck must be validated against the check they modify, and replay must never re-derive outcomes. |
| D45 | **Only a plain `failure` can be pushed**, not a critFailure, an automatic failure or an opposed check. | A fumble already carries a consequence; pushing an impossible task makes no sense; opposed pushes have no clear meaning. |
| D46 | **d20 rounding is half away from zero**, and the **campaign difficulty modifier counts inside the ±40 cap**. | Symmetric conversion around 50; one place where all modifiers meet keeps the cap meaningful. |
| D47 | **Luck rerolls and pushes on opposed checks are deferred to M4** (combat), where attack vs Dodge makes the rules concrete. | Avoids guessing a design the combat milestone will define. |
| D48 | **Frightened applies its −20 whenever present** until scenes track line of sight (M4/M5). | The engine can't know "in view" yet; erring towards the penalty keeps fear meaningful. |
| D49 | **Rewind's fork starts with a `BranchForked` event.** | The fork point is visible in the log and timeline, and the reducer ignores it, so state hashes still match a straight replay. |
| D50 | **Point-buy validates totals**: the sheet stores trained totals, and the validator checks that some split into the core and interest pools exists. Unspent points are warnings. | The sheet schema has no core/interest split; a feasibility check gives exact errors without adding one. |
| D51 | **`fantasy-core` lists no plugins and no class mode yet.** Spellcasting is M7; classes need `classes.yaml`. | The pack validator rejects unknown plugins, so the pack only claims what the build supports. |

## Implementation decisions (M2)

| # | Decision | Why |
|---|---|---|
| D52 | The turn pipeline (`llm`) takes the campaign store and canon through small interfaces (`TurnStore`, `TurnCanon`); the app passes `CampaignStore` and `CanonQueries`. | Keeps the spec's dependency rule (`core, engine, memory ← llm`): `llm` never imports `storage`. |
| D53 | Canon (entities, facts, turns) lives only in storage projections; the engine tracks **presence** through `scene.positions` (id → zone). Exploration scenes reuse the zone shapes from spec 03. | Spec 01 keeps unbounded canon out of `GameState`; validation still needs to know who and what is here. |
| D54 | M2 implements the exploration subset: `check`, `examine`, `search`, `interact`, `move`, `wait`, `talk`. A `talk` with an approach rolls opposed against an actor with a sheet, or a plain Normal check against a canon-only NPC. Dialogue mode proper waits for its milestone. | Smallest set that makes exploration playable; canon NPCs have no stats yet. |
| D55 | Talking needs earshot (same or neighbouring zone). A check aimed at a zone (a climb) moves the climber on success, only from the zone next to the climb. Validation projects earlier moves ("go there, then talk"). | Found in the first playtest: the rules allowed talking across the map and climbs that went nowhere. |
| D56 | After two failed repairs, clarification options are built by the engine from its legal alternatives and labelled locally (`describeAction`), not phrased by the parser. | Saves a model call on an already failing turn and can't produce illegal options. |
| D57 | Guard v1 answers through a `report_canon` tool; an unusable report shows the passage unchecked. New named entities become stubs placed in the current scene; new facts attach only to known IDs. | Tool calling is the most reliable structured output across providers; stubs keep "nothing exists until written" without blocking play. |
| D58 | The hand-authored world's premise is the world bible (section 4), stored as canon entity `concept:world-bible`. | Section 4 needs a stable source; world generation (M5) will replace it. |
| D59 | Until the server exists (M3), the terminal loop reads providers from `WYRD_HOME/config.json`, keys from `WYRD_HOME/secrets/`, and appends usage records to `WYRD_HOME/usage.jsonl`. | The spec puts these in app.db, which arrives with the server; the file layout matches spec 01 otherwise. |
| D60 | The Anthropic adapter uses the official SDK. Forced tool choice becomes `auto` plus an instruction (current models reject forced tool use); sampling parameters aren't sent; server-side refusal fallbacks are on for models that support them; a refusal is a `refused` error so the router moves on. Assistant content (thinking blocks included) is echoed back unchanged on the next turn. | Current Claude API behaviour; editing history would invalidate thinking blocks. |
| D61 | ChatGPT plan details were checked against OpenAI's token-sharing guide on 2026-10-28 (see spec 09). Still unverified: the refresh request's form fields (standard OAuth refresh grant plus `resource` is used) and the JWKS location (OpenID discovery). | Spec 09's VERIFY rule. |
| D62 | A provider that returns `usage_limit`, `not_eligible` or `auth` is benched for an hour (configurable) instead of being retried. | OpenAI documents no reset time for the plan limit and says not to retry or loop. |
| D63 | An offline provider (keyword matching for every role) lets `wyrd play --offline` run with no keys. | Development and demos without spending plan usage. |
| D64 | The DeepSeek playtest config explicitly uses `thinking: "disabled"`; the generic OpenAI-compatible adapter passes an optional thinking-mode setting from config. | A real host probe confirmed that DeepSeek's default thinking mode rejects the parser's forced `tool_choice`. Non-thinking mode supports it and is appropriate for the short parser/guard calls. Other compatible providers keep their existing defaults. |
| D65 | Retry malformed provider output once on the same target when the adapter marks it retryable, within the existing router attempt budget; then fall back. | Intermittent malformed DeepSeek parser JSON previously triggered immediate fallback despite the adapter's retryable flag. Regeneration happens before engine resolution and cannot repeat an action or roll. |
| D66 | M3 uses explicit passcode sessions on every device, including loopback; setup and account/key changes additionally require a loopback peer and hostname. SIWC starts with POST and returns a browser link. | Safe first-run setup and CSRF protection without silently trusting a local hostname. The loopback bypass in spec 14 was optional. |
| D67 | M3 journals turn-request IDs and numbered SSE messages in app.db. Campaign state and narration remain event-log projections in campaign.db. Interrupted jobs finish with a recovery message on restart; the browser refreshes GameView. | Resumable streams and durable deduplication without executing an uncertain action twice. |
| D68 | Model config and usage import from CLI files into app.db; CLI files remain intact. Dialog styles use per-page CSP nonces. Guard flags offer regeneration; retcon/edit waits for canon-editing events. | Preserve existing terminal playtests, keep account secrets server-side, and avoid bypassing event sourcing to implement a UI shortcut. |
| D69 | The default web creation path is pitch → generated world/origins/backgrounds → review → play. Names start blank; character name is optional, with an explicit generated suggestion on review. The original Ashford fixture remains available only through the explicit quick-start API for tests. | Owner correction: Wyrd is any-genre; the M3 fantasy fixture must not define the product's creation experience. This brings a bounded opening-site slice of M5/M6 forward without claiming those milestones complete. Code owns budgets and freezes generated content; NPC secrets remain server-side. |
| D70 | Dialogue resolves IDs and supplied display names; GameView includes names only for speakers already referenced in visible narration, in addition to its current scene. Reading uses restrained strong emphasis for known names/places and narrator-marked important details. Hover/focus/tap reference cards are scheduled with M5 Codex/knowledge work. | Owner request to improve readability now and defer detail cards. Fixes the generic "A voice" fallback without exposing the full NPC registry. Text is escaped; no general Markdown/HTML execution. Narrator prompt is versioned `narrator@2`. |
| D71 | M4 is built in steps A–G (`docs/superpowers/plans/2026-10-28-m4-roadmap.md`). Infection, fracture setting and healing, healing over days, short and long rests, and permanent injuries move to M5. Chases also move to M5. M4 records `fracture` on wounds and applies its penalties. | Infection, fracture setting and healing, healing over days, rests and permanent injuries need the calendar and world ticks. Chases need clocks. |
| D72 | Wound effects live in `tuning.combat.woundEffects` and are keyed by location kind (head, torso, arm, leg). Body-plan locations map to a kind. The humanoid plan is built in as `core:humanoid` (spec 05); packs add extra plans in `bodyplans.yaml`. `findBodyPlan` matches by exact id, then by local id, then falls back to the humanoid. | One effects table serves every body plan. Other plans reuse the same kinds in step D. |
| D73 | Cut damage adds +1 Bleeding even to wounds that otherwise don't bleed. The arm-serious `bleedingIf` replaces that bonus, and burn never bleeds. A wound's bleeding adds to the current level, capped at 3. Severing needs cut damage ≥ 4 × WT. | Follows spec 03's damage-type rules. The cap keeps stacked wounds within Bleeding 3. |
| D74 | Event shapes and item defaults: `HpChanged` stores the resulting HP, and the reducer clamps it to the effective max. `WoundWorsened` carries its new `hpMaxReduction`; the emitter computes it, and lethal counts as critical. A wound stores its `side` and its `penalty` (scope and value) as stamped at infliction. Weapons get `strengthBonus`, which defaults to true except for skill `ranged`. Unarmed is `1d3 blunt` from tuning. | Events carry their results, so replay doesn't recompute them. A stamped penalty means later retuning doesn't change old wounds. |
| D75 | Simple injuries still run lethal checks, and a repeat critical at one location is still lethal. Spec 11's simple mode simplifies wound effects (flat −10/−20/−30 to all checks, Down on a critical, no bleeding, fractures or severing), not whether a character can die. | Simple mode changes how much detail injuries carry, not whether a character can die. |
| D76 | Existing wound penalties apply to later checks, including the END Down and lethal checks ("physical" covers str/agi/end). A lethal check ignores the wound it is testing (tag `ignore-wound:<id>`), so one injury isn't counted twice. | One injury shouldn't count twice against the check that judges it. |
| D77 | A damaging hit counts as "while Down" only when HP was already 0 before the hit. The severity steps up once and is capped at critical. | The check uses HP at the start of the hit, so the hit that takes HP to 0 isn't also a hit while Down. |
| D78 | Bleeding at 0 HP: every tick at 0 HP rolls END (Normal), even when nothing can worsen. On a failure, Down becomes Unconscious (Down is removed), and Unconscious makes the most severe wound lethal. A tick that takes an already-Unconscious actor from above 0 to 0 only lowers HP; END rolls start on the next tick. | Each tick at 0 HP is a chance to worsen. A tick that brings an unconscious actor to 0 HP only lowers HP, so the END roll waits for the next tick. |
| D79 | Sheets carry `equipment` (held main and off, worn, carried), filled from the archetype kit at creation. The first weapon is held, and all armour is worn. | Combat needs to know what is held and worn, so the sheet records it from creation. |
| D80 | Combat state is one `GameState.combat` block. `CombatStarted` sets it, `CombatChanged` replaces it after each action or turn change, and `CombatEnded` clears it. Positions still move with `EntityMoved`, and HP and wounds use the injury events. | Replay stays trivial and the reducer can't drift from the rules. Fine-grained AP and engagement events would add many types for no extra truth: the actions that caused them are already in the log. |
| D81 | A fight uses the open scene's zone graph. `propose_zone_map` waits for lazy location generation (M5), because every scene today (authored and generated) already has zones, props and edges. Exits are zones tagged `exit`. | The spec's "reuse the canon zone map" path is the one that always applies now. No model call is needed to start a fight. |
| D82 | Initiative is an AGI check with an AWA-difference modifier, which puts the target at AGI × 5 + AWA × 5. The order is by degree, then margin, then AGI, then the PC. Initiative groups, Delay, Ready, Hide, Use item and abilities/spells wait for later milestones (spells are M7). | It reuses the check machinery exactly. The skipped actions need systems that don't exist yet (inventory consumables, plugins). |
| D83 | An attack must succeed and then beat the defender's Dodge or Parry. The defender automatically uses the better of the two, and Parry only works against melee with a melee weapon. Defend gives +20 and an extra defence-only reaction. Luck on opposed checks (D47) stays deferred. | The defender's choice is mechanical, so the engine makes it. A Luck reroll mid-attack needs a pause-and-offer flow in the UI. |
| D84 | A hardcore PC facing instant death (critFailure on the lethal check) automatically spends 2 Luck to downgrade the wound, if they have it. | Spec 03 allows it, and asking mid-resolution would need an interrupt the pipeline doesn't have yet. Spending it is always the right call. |
| D85 | Morale: the whole group rolls WIL (Normal; −20 for cowardly; berserk is immune) when its leader is out of the fight, when half the group is out, or after a successful Intimidate. Failure means fleeing and a critFailure means surrender. Fleeing combatants no longer count as fighting. | Group morale ends fights realistically without a long tail of stragglers. |
| D86 | Each player input is one whole turn, and unspent AP lapse. After it, AI combatants (enemies and companions) act until the PC's next turn. One narrator call writes two paragraphs: the PC's turn, then everyone else's. Companion directives are M6. | It keeps one model call per turn and matches the spec's two-passage pacing. |
| D87 | Defeat outcomes come from a seeded, weighted table keyed by the enemy's intent (rob, capture, arrest, kill, driveOff, prey). Every outcome turns lethal wounds into persistent criticals, leaves the PC at 1 HP and awake, advances time, and may take items. It always creates a quest entity as the new hook. Victory loot is the fallen enemies' carried gear (loot tables come with M5's economy). | Spec 03 requires that defeat always costs something and always opens a thread. The stat blocks already carry intent. |
| D88 | Legacy continues in the same campaign. A new PC actor enters the current scene, and the dead PC becomes a canon `npc` entity (status dead) with a grave fact. The engine writes the obituary from canon, with no model call. | The world, its people and its history carry over intact. A deterministic obituary can't invent facts. |
| D89 | Creatures live in a single `creatures.yaml` (spec 05 suggests `creatures/*.yaml`). Natural weapons and hides compile into the item tables as `pack:creature-weapon` and `pack:creature-hide`. Scene entities name their stat block, group, leader and intent in canon `data`. Unknown entities fight as a built-in commoner. | One file is enough for ten-odd creatures. Treating natural attacks as items lets the hit code stay item-driven. |
| D90 | GameView shows the PC's side exactly but enemy health only as five perceived bins (0, ¼, ½, ¾, 1). Quick start (the test API) accepts `world: tavern-brawl`. Servers accept a fixed `seed` for tests only. | Knowledge layers: the PC sees how hurt someone looks, not their HP. A fixed seed makes the browser tests deterministic. |
| D91 | A fight doesn't end while a party member is dying: their death clock keeps running after the last enemy falls, and allies (AI included) try first aid, stabilising them or not. After a fight the party survived, unconscious members come round at 1 HP or more. Flee is Disengage plus Move and doesn't provoke. A melee strike on someone in the same zone gets an automatic engage. Called-shot locations are validated before anything is rolled. A dead PC can't take turns. Bleed lines show HP only for the party. | Fixes from the M4 review. Without them, a victory or a flight dodged hardcore death, the most common opening attack wasted a turn, and an enemy's HP reached the browser. |
| D92 | World simulation state lives in `GameState`: clocks, factions, quests, social edges, NPC minds, rumours, PC knowledge and the threat. Canon entities and facts stay in projections. States from before M5 (old snapshots) are upgraded on load. | Ticks, rumour spread and who-knows-what must be pure and replayable, so the engine needs them in state. The projections (codex, retrieval) are rebuilt from the log. |
| D93 | Stage 1 is two `worldGen` calls: the opening (as in M3), then one validated world bible covering regions, sites, routes, factions, threat, key NPCs, hooks and the form of address. Spec 06 suggests six smaller calls. Names go through a registry (normalised edit distance ≤ 0.15) with one retry. If the bible fails, the campaign starts as a single site. | One extra call keeps creation fast and the bible internally consistent. A missing bible shouldn't block play. |
| D94 | Lazy generation in M5: a site's arrival place is generated on first travel, and stubs are elaborated when the PC talks to or examines them, both committed before the turn resolves. `generate_npc`, `generate_item` and `propose_zone_map` wait (every scene already has zones). | These cover play across sites, which is the acceptance criterion. Asking about unknown people and items needs parser support that belongs with dialogue mode. |
| D95 | Travel is a Navigation check whose difficulty comes from route danger and pace. Failure costs 25% more time, and with danger ≥ 2 (or any critical failure) it brings a road encounter: a road scene with foes (the pack's robbers, or ordinary thieves). The journey pauses there and resumes when the player travels again. Foes don't attack first. | The check gives the pace/time/danger trade-off of spec 06 without a separate random roll, and the player decides whether to fight, talk or flee. |
| D96 | The calendar defaults live in tuning (12 months of 30 days, seasons, dawn and dusk); pack calendars come later. The hourly tick only records itself (NPC schedules and lighting come later). The daily tick handles rumours, faction goals, the threat's pace and weather. The weekly tick turns finished faction goals into news. Long skips run at most 60 daily ticks. | These are the parts of the world simulation that M5's acceptance and memory need. Schedules need NPC routines that don't exist yet. |
| D97 | Each rumour keeps its holders and the version each one heard. It hops along social edges with probability heat × strength × (1 − secrecy), and memberOf links co-members at half strength. Lies and threats are urgent and move 3× faster along reportsTo. Told memories of importance ≥ 3 (persuade, deceive, intimidate) start a rumour with the NPC told. Seeded distortion drops names, inflates numbers or adds hedges. | This implements spec 07 directly. The holders' versions make distortion visible per person. |
| D98 | Retrieval embeddings are a local hashed bag of words (`hash-512@1`) computed in the projections, so retrieval works offline and in CI. A model-backed embeddings role can replace them, since vectors are a cache. Bun's SQLite has FTS5, so the TF-IDF fallback isn't built. | Spec 07 allows a fake deterministic embedder for offline retrieval tests; using it in production too keeps play working without an embeddings model. |
| D99 | Pyramid summaries are written right after the turn that crosses a boundary, not by a background job. Offline, or on failure, the summary is mechanical (first sentences). Regenerating stale summaries after a retcon is deferred. | It's simpler and deterministic, and the summarizer is cheap. Stale summaries only affect wording, never canon. |
| D100 | The narrator sees all public facts about present (perceivable) entities, but only the PC-known facts about absent ones. Whoever the PC is talking to appears with their own top memories and disposition, and speaks only from them. The full `npcDialogue` role with its tools is dialogue mode (later). | Knowledge layers are kept without a second model call per line. |
| D101 | Guard v2 blocks secret reveals (the shown detail names only the fact ID) and crossed lines. It records witness memories, but only for people present, and accepts narrative objectives only for an active quest's current objective. `approvalDeltas` are parsed and ignored until companions (M6). | This is the spec 07 policy, without leaking secrets in the flag shown to the player. |
| D102 | Codex retcons apply only to descriptive facts the PC knows: not engine-sourced facts, zone notes or secrets. A retcon supersedes the old fact, and the PC learns the new one as "deduced". The form of address is stored on the world-bible entity, and the player can edit it. | Engine state is corrected by rewinding (spec 07). The address is world-level presentation data. |
| D103 | Offline previews and tests use fixed, genre-neutral stand-ins for the world bible, locations and elaboration, labelled as not AI generation. | Offline previews and CI need to travel and remember without a model. |
| D104 | A character stays a draft on the creation draft until the campaign starts; every path (quick, form, session zero) edits the same `DraftSheet`, and the server builds and validates it with `validateCreation` on every save. Generated worlds' quick path is the origin and background picker; packs ship pregens (`pregens.yaml`: a person on top of an archetype's numbers). Changing background in the editor resets attributes and skills to its suggested training. | One validator, no events until the player commits, and generated worlds have no authored people to offer as pregens. |
| D105 | Session zero is one forced `interview_step` tool per answer (proposals for identity, attributes, skills, talents, appearance and hooks, plus the next question and `done`), not six separately callable `propose_*` tools. The engine applies each part only if it adds no creation-rule error in that part, and refusals go back to the interviewer on the next step. Gear comes with the background (its kit). The form wizard's "suggest" buttons are one `sessionZero` call per field, applied the same way. Offline, a labelled fixed interviewer and fixed suggestions stand in (D103). | A single forced tool works on every provider we route to (some reject free tool choice with thinking on), and per-part checks keep good proposals when one part is wrong. |
| D106 | Backstory hooks become canon when the campaign starts, after the world bible: the `worldGen` role places each hook at a site and maybe a faction (`place_hooks`), with a fixed fallback offline or on failure. Rivals, bonds and missing people are NPCs (a missing person's whereabouts are a secret fact); a debt is owed to a person or a faction and runs a visible deadline clock; a secret is a concept with a secret fact. The PC knows every hook entity. | The bible is generated before the character exists, so placement is the stage-2 step that consumes hooks; keeping it at commit means the player can edit hooks freely until then. |
| D107 | Progression is engine-side (spec 04): XP for completed quest stages (main 8, faction/personal/companion 5, side/job 2, plus 2 for a personal goal), won fights (1 + one per three enemies, up to 3), reaching a new site (1) or learning of a region (2), and closing a chapter (2). XP is shared by the living party; hybrid awards half, rounded half up. Use-based marks need a Normal-or-harder success with stakes (combat, opposed, Hard+ or a push) and no Luck reroll; a long rest (8 hours' wait outside combat) or a chapter close rolls them. Use-based campaigns get a talent every two chapters and an attribute point per arc, spent as free purchases. Class mode waits for packs with class data (M7). Costs and awards live in `tuning.progression`; purchases are `AdvancementBought` events carrying the recomputed derived stats, so the reducer needs no tuning. | Engine-awarded XP keeps narration from granting power, and every number stays tunable and replayable. |
| D108 | Recruiting is a `recruit` exploration action the parser proposes; the engine accepts it only if the NPC is present, the party has room (3), and they're willing: attitude toward the PC of at least 25, a friend/family/bond edge (backstory hooks make these), or an active quest objective to recruit them. The reason is recorded as a canon fact. A recruit who isn't already an actor gets a full sheet from the pack background whose description best matches them, at the creation budget. Their values, likes, dislikes, betrayal trait and personal quest are written once after the turn (`worldGen`, or a fixed profile offline). | Recruitment is a rule, not narration; full sheets keep companions on the PC's rules, and profiles need a model call, which can't happen inside the pure engine. |
| D109 | Approval comes only from guard-proposed deltas for companions present in the scene, capped at ±10 per event and ±20 net per scene. Crossing −50 owes a confrontation scene, −75 makes them leave (or betray, if their profile allows), +50 starts their personal quest, +75 marks them loyal. Owed scenes and at most one banter per scene are required beats on the next turn. Manual control marks a companion player-controlled in fights, so their turn takes the player's input; AI companions follow a standing order (follow, aggressive, defensive, support, hold) that weights the tactics AI. | The spec 04 thresholds, with beats on the next turn because approval is judged after narration. |
| D110 | M7's event registry and reducer are split into domain modules: `core/schemas/domains/{subsystems,survival,spellcasting,living,classes}.ts` export event-payload maps that `events.ts` spreads, and `engine/src/reduce/{...}.ts` export `Pick<Handlers, ...>` maps that `reduce.ts` spreads. Shared reducer helpers live in `reduce/helpers.ts`. | Seven M7 workstreams add events and handlers at once. Domain modules keep their edits disjoint, while the mapped `Handlers` type still makes a missing handler a compile error. |
| D111 | M7 presets live in `core/presets.ts` (Story, Standard, Simulation and `custom` with the base label). Campaign settings change through `PATCH /api/campaigns/:id/settings`; a refused structural change returns 409 with the exact path and reason, and the UI greys those fields and shows the reason. Changing any toggle after a preset marks the campaign `custom (from X)`. | Spec 11/12: presets must be one click, every non-structural toggle must stay live, and the player must see why dice/progression cannot change. |
| D112 | d20 legibility is data, not string parsing: `MechanicsLine.roll` carries `{ die, sides, natural, modifier?, total?, target?, dc? }` and `GameView.resolution` carries the campaign's dice mode. The d100 text is unchanged, so existing campaigns read exactly as before; the three golden combat fixtures were re-recorded deliberately. | The UI must never show a d100 percentage or an unexplained DC in a d20 campaign, and the mechanics log stays a pure engine projection (spec 02/13). |
| D113 | Content dials are compiled into one compact policy block injected into narrator, parser-adjacent prose, world generation, summaries and NPC dialogue, and the canon guard rejects configured lines and veils deterministically (`memory/content.ts`). Lines are never named, quoted or implied; veils cut away. | Spec 12 says dials are injected everywhere and enforced by `linesCrossed`; the engine, not the model, decides what passes. |
| D114 | Class progression is pack data (`classes.yaml`, six classes × ten levels) plus `ClassLevelGained`: levels grant class-skill points, any-skill points, features and +1 attribute at 4/8. Use-based and hybrid keep their marks/improvement paths; the progression mode remains locked at creation. | Spec 04 requires all four modes without converting state between them. |
| D115 | Living World completes faction goal clocks weekly, publishes faction/festival/life news as rumours, runs NPC marriages/births/retirements/deaths and refreshes the job board; the threat clock freezes while `story.mode === "livingWorld"`. Downtime (`train`, `craft`, `work`, `research`, `carouse`, `recover`) is resolved by the engine into `DowntimeResolved` plus ordinary events (`CoinsChanged`, `ItemTransferred`, clocks, conditions, HP). | Spec 06: off-screen change is canon and news, and downtime outcomes must never be model-decided. |
| D116 | The spellcasting plugin keeps its state under `flags.spellcasting`, its data in `spells.yaml` (30 spells, four schools) and uses ordinary camel-case events (`SpellCast`, `SpellMiscast`) rather than slash-namespaced plugin event names. Strain is 1/2/4 HP by tier, AP comes from the spell in combat, a critical failure miscasts (backlash damage, exhaustion, broken concentration). The parser sees the known-spell list; the sheet shows school, tier, AP, range and strain. | The engine already has one event registry; a second naming scheme would complicate replay. Effects stay engine-owned: the model proposes a spell and targets only. |
| D117 | `Wound` gained optional `healingDays`, `infected` and `treated` so pre-M7 snapshots still validate. A daily tick heals wounds (simple injuries at half time, treatment accelerates), rolls infection on untreated serious+ wounds, stalls unset fractures, adds `core:infected`/`core:fractured`, and can leave a permanent injury when a critical wound heals untreated. Rest is an exploration action; long rest treats wounds, restores HP and clears exhaustion. Every part obeys its subsystem toggle. | Spec 03/11: wounds must heal over game time and the four injury toggles must each stop their rule without deleting state. |
| D118 | Inventory and economy are projections in `GameState.inventory` / `state.economy`, with events (`ItemTransferred`, `CoinsChanged`, `ItemConditionChanged`, `ShopOpened`, `ShopStockChanged`, `BargainStruck`). Encumbrance uses STR × 5 kg and the three bands; ammunition is counted and half of spent arrows/bolts return on a Search; weapons wear on a fumble and armour under a blow exceeding protection by 5; the starting settlement opens the pack's first shop (economy.yaml) with a 50-coin purse, and buy/sell/haggle are exposed by the API and Inventory tab. Wealth-level auto-purchases and seasonal price drift are data-ready but not yet enforced. | Spec 11 asks for every inventory/money dial; this slice makes the Standard/Simulation modes playable end to end while leaving the Story wealth rules explicit rather than guessed. |
| D119 | Pack themes (`theme.yaml`) are validated into `CompiledPack.theme`, exposed as `GameView.theme`, and mapped to CSS custom properties with light/dark variants; the fantasy palette is contrast-tested. A campaign without a theme keeps the app defaults. | Spec 13: the genre sets the mood, and all themes must meet WCAG AA. |
| D120 | Timeline, branches, named saves, `.wyrd` export/import and daily backups live in `storage` with `fflate` for the archive; the API exposes them and the Timeline tab lists turns, forks and saves. Hardcore campaigns refuse rewind/fork. | Spec 14: the event log is truth, so a fork is a branch copy and an export is a portable campaign. |
| D121 | Ordinary-NPC scene responses are a deterministic bounded phase after combat actions/AI and before the next player input. Failed assaults count. Optional reaction profiles select protest, help, retreat or intervention; incident/round/actor metadata lives on existing witnessed memories. Neutral retreat respects normal movement costs; entering combat rolls initiative and gives no free attack. Active companions keep M6 approval/control. | The parlor playtest showed that remembering an assault did not make anybody respond. Persistent incident keys work at combat's zero elapsed minutes and avoid a parallel companion system. |
| D122 | Keep D86's one normal narrator call and player-then-others order, but replace mandatory long combat paragraphs with significance-based length. Provide selected response intents and safe shared speaker history. Omitted/malformed selected speech gets an engine-supplied fallback before guard checking. Narration rerolls never add witness observations. Full private npcDialogue tools remain deferred under D100. | Speech and consequences must survive silent prose or a provider outage, without dumping private NPC minds into narration or inventing outcomes to make a scene interesting. |
| D123 | Commoner combat intent defaults to driveOff, while explicit NPC/creature intent wins. Opposed maneuvers report their contest outcome separately from raw roll degrees, and the UI receives all generated combat mechanics lines. | Missing intent previously escalated ordinary people to kill, and a won grapple could be labelled Failure with the resisting roll hidden. |
| D124 | M3 review fixes: the scene location's public facts (opening passage, zone descriptions) enter narrator and guard context; a reroll hides turns and facts asserted after the re-narrated turn; only the PC or a commanded companion may be the acting `actorId`; guard flags show the quoted line plus a fixed reason; mechanics render under the passage and show-the-math defaults on. | The player reads the opening passage, so the models must see it or turn one can contradict it; a past reroll must not use the future; a parser misparse must not move an NPC; guard detail can restate a secret it was given to check; spec 13 and D13 already settled reading order and the math default. |

## Wyrd 2.0 (owner interview, 29 October 2026)

After playing M7 on deepseek-flash, the owner judged the game "so lacking" next to their own ChatGPT RPG sessions. A 72-question interview redesigned the game; the full spec is `docs/superpowers/specs/2026-10-29-wyrd-2-design.md`. These supersede earlier decisions where they conflict. D4 (heavy crunch everywhere) becomes pack-dependent; D3 (code owns hard state) stands.

| # | Decision | Why |
|---|---|---|
| D129 | **Player authority, in order:** (1) whatever the player writes at creation is canon; (2) explicit GM mode (`/gm` or a clear correction) applies a retcon with an Undo; (3) otherwise "yes, and…" with consequences. Never "ask your GM". | The first real campaign lost the player's yellow lantern ring and refused to change it. |
| D130 | **Cosmic Level scale** 1–20 with huge gaps (human → multiversal), open above 20, plus ∞. d20 resolution compares levels: Δ0 is a fair roll, ±1 is ±10, Δ≥2 is automatic, and Δ≤−2 fails unless an exploit is cited. Ability ranks 1–10 add +1…+5 at Δ0; the sheet shows a cosmetic power rating. | The owner plays from street level to omnipotent and wants "fair D20" at every scale without stakes drifting away. |
| D131 | Levelling up has four routes: story milestones (the GM proposes, the player accepts), XP, breakthrough rolls in training or time skips, and GM mode. | It matches how the owner's campaigns grew. |
| D132 | Dice depend on the pack: `fantasy-core` stays d100; source and new campaigns use d20 with Levels. | The gritty pack and its tests stay meaningful; the owner plays d20. |
| D133 | The death rule is chosen per campaign at creation, hardcore by default. | The owner always asks for hardcore. |
| D134 | A Level-∞ sovereign never rolls. Stakes come from **avatars** (chosen level, real dice, death ends the run; sovereign intervention marks the run unsealed) and from **sealing** (an effective level). | Omnipotence has no rivals; avatars and seals bring the dice back. |
| D135 | **Source-story mode** alongside original worlds: creation researches an existing story into the world bible, and the prose follows the source's style. | The owner plays inside existing novels and comics and loved ChatGPT matching each one. |
| D136 | Lore comes from the official MediaWiki APIs (Wikipedia, Fandom) at 1 request/s, cached once globally in `WYRD_HOME/lore-cache/`, stored as summaries with source links, with the model's knowledge as a low-confidence fallback. The "original content" invariant applies to shipped repo content; runtime lore is per-user data and is never committed. | It works with any model, it's cheap after the first fetch, and it's visible and correctable in the Codex. |
| D137 | Canon events are clocks that resolve unless the player intervenes; canon characters act on their own and stay in character. Continuity is "greatest hits" by default. | "Follows the novel closely", while still letting the player bend it. |
| D138 | Loyal companions (Ari) have no approval meter and never leave. They advise, argue and take **delegated tasks** that resolve with real rolls during time advances. | Ari is the owner's right-hand advisor across their whole campaign. |
| D139 | **UI 2.0:** Caves of Qud's modern-UI structure (dense status strip, ability hotbar, coloured keywords, full-screen tabbed menus, centred event pop-ups) with ChatGPT-style cards and a modern finish; Reader layout by default, keyboard-first; a fixed shell plus a per-campaign theme of one dark hue and fixed-meaning accents. Built with tasteskill directions and impeccable. | The owner judged the current UI "real bad" and named these references. |
| D140 | At creation the GM proposes the subsystem toggles for the setting (survival on for an apocalypse, off for cosmic DC), the theme, the resolution, the death rule and the starting Level; the review step lets the player override any of them. | Torches and hunger make no sense for a Green Lantern, but they do for an apocalypse. |
| D141 | A campaign holds several worlds (`worldId` on entities, facts, clocks and lore); v1 creates one. | An omnipotent PC opens new universes without starting over. |
| D142 | ChatGPT share links can be imported: decode the page, extract the PC, companions and history, then review at creation. | The owner's existing campaign (Ethan Hunt and Ari) continues in Wyrd with no recap pasted. |
| D143 | "Done fixing" = a side-by-side replay of the owner's chat inputs through Wyrd's GM (an eval) with systematic losses fixed, plus a 20-turn owner playtest judged at least as good as ChatGPT. M8 waits until then. | The owner's own chats are the benchmark. |
| D144 | **The GM-with-tools turn** replaces parser → narrator → guard for new turns. One GM model streams prose and calls engine tools (`roll`, `act`, `change_state`, `retcon`, `lookup_lore`, `observe`, `time_skip`, `show_card`, `offer_choices`, later `delegate`). The engine validates and commits; prose may not claim unrecorded changes, and a non-blocking structural check flags them without ever rewriting. There's no separate OOC helper, no `MAX_CHARS` truncation, choices follow a policy (`gm` default), and the UI shows a backup-model badge on fallback. | A fixed action menu could never cover powers at every scale; the owner's ChatGPT sessions feel good because the GM is free, and Wyrd's job is to make the dice and memory real. |
| D145 | Structured model output feeds validation errors back for `tuning.structuredOutput.repairs` (2) more attempts before failing. | deepseek-flash's bad tool arguments used to fail creation outright; a bounded repair loop turns most of them into a valid call without hiding a genuinely broken provider. |
| D146 | Player-written starting gear becomes `player:` GearDefs in the campaign's frozen pack and ordinary carried items. Names are slugged (`item-<n>` when non-Latin), case-insensitive duplicates merge, and session-zero gear merges append-only. | The player's yellow lantern ring must be a real thing the inventory, shop and prose can see, not a note next to the sheet. |
| D147 | Creation writes the player's gear, background, backstory, appearance and pitch as pinned `source: "player"` facts, and every prompt carries them in a capped "Player canon" section that outranks other facts. | The player's own words are the top canon (D129), so no summariser, retcon or trimmer may quietly lose the lantern ring or the backstory. |
| D148 | Generated worlds get an optional model-proposed starting kit (gear, per-archetype kits, currency, one shop), merged before the pack hash; a failed call keeps the old empty behaviour. | A generated world that starts with no items and no shop feels like a demo; keeping the call optional means one bad response never blocks creation. |
| D149 | GM-invented items are `campaign:` GearDefs defined by `ItemDefined` and merged into the item catalog by `catalogWith`, so inventory, shops and prompts all see them immediately. | A GM at any scale must be able to create gear mid-turn without editing the frozen pack or inventing a second item store. |
