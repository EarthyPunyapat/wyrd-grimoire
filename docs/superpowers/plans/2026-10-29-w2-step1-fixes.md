# Wyrd 2.0 — Step 1: fixes that survive the rebuild — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Creation never loses what the player wrote, wizard-generated campaigns start with items and a shop, and structured model calls survive deepseek-flash's bad output instead of failing creation.

**Architecture:**
- A shared "call a tool, validate with zod, feed the errors back, retry" helper replaces the two hand-rolled loops in `world-generation.ts`.
- Player-written gear becomes real pack items (namespace `player:`) plus pinned `source: "player"` facts, which the assembler always includes.
- Generated worlds get an optional, separately-called starting-kit proposal that `compileGeneratedWorld` merges before hashing.
- None of this touches the turn pipeline, which step 2 replaces.

**Tech Stack:** Bun, TypeScript, zod 4, Hono, React, `bun test`, FakeProvider.

**Spec:** `docs/superpowers/specs/2026-10-29-wyrd-2-design.md` (§4 step 1, §5.3 rule 1, §13).

## Global Constraints

- `packages/engine` stays pure: no network, filesystem or clock.
- Every new tuning number goes in `packages/core/src/tuning.ts` (`Tuning` type and `defaultTuning`), never inline.
- Tests stay offline. Use FakeProvider via `RoleRouter`, wired as in `apps/server/test/world-generation.test.ts:26-35`.
- Each new event uses an existing event type. This plan adds none.
- `bun run check` (typecheck → lint → test → pack validate) is green at every commit.
- Behaviour that changes the spec gets the spec file updated and a line in `docs/decisions.md` in the same commit.

## Review Focus

1. **A player types gear with the same name twice, or names that only differ in case.** Expect one item per distinct name and quantities that add up. No crash, and no duplicate ids (Task 3 test `dedupes gear names`).
2. **A player types gear with emoji or non-Latin characters** ("雷の指輪"). Expect a valid slug id (fall back to `player:item-<n>`) and the name kept verbatim (Task 3 test `slugs non-latin names`).
3. **The starting-kit call fails or returns rubbish.** Expect the campaign to still be created, with no shop and the archetype kit empty, exactly as today (Task 5 test `kit failure keeps creation working`).
4. **A model keeps returning the same invalid arguments.** Expect exactly `1 + repairs` attempts, then an `invalid_output` error with `retryable: false`, and no infinite loop (Task 1 test `gives up after the configured repairs`).
5. **Player canon is huge** (a 4,000-char backstory plus 12 gear entries). Expect the section to be capped at the budget and never to push out section 13 "This turn" (Task 4 test `player canon is capped`).

**Files:**

- Test: `packages/llm/test/structured.test.ts`

**Interfaces:**
- Produces:
  ```ts
  export type StructuredSpec<T> = {
    role: Role;                       // from @wyrd/core
    tool: string;                     // tool name, forced via toolChoice {name}
    schema: z.ZodType<T>;
    instructions: string;
    input: string;                    // first user message
    promptVersion: string;
    maxOutputTokens?: number;         // default 16384
    maxChars?: number;                // default 80000
    repairs?: number;                 // default defaultTuning.structuredOutput.repairs
  };
  export async function proposeStructured<T>(router: RoleRouter, spec: StructuredSpec<T>, opts?: { campaignId?: string }): Promise<T>;
  ```
- Behaviour:
  1. An attempt fails when the router throws a `ProviderError` with `code === "invalid_output"`, when the completion has no call named `spec.tool`, or when `schema.safeParse` fails.
  2. On a failure with attempts left, append the assistant's tool call, if any, as `{role:"tool", toolCallId, name, content: JSON.stringify({rejected: true, errors})}`, or else a user message. The `errors` are `z.prettifyError(...)` or the provider's message. The message ends: `Call ${tool} again with corrected arguments.`
  3. When the attempts run out, throw `new ProviderError("invalid_output", <last error>, false)`.
  4. Other `ProviderError` codes are rethrown unchanged, because the router already handled their fallback.

- [ ] **Step 1: Write the failing tests.** Script FakeProvider rules with `role: "worldGen"`. Use a schema `z.object({ name: z.string().min(1) })` and tool `"propose_thing"`.
  - `returns the first valid call`: one good tool call gives `{name:"x"}`, and `fake.calls("worldGen").length === 1`.
  - `repairs a bad call with the validation error`: first `{toolCall:{name:"propose_thing", args:{name:""}}}`, then a good call. The result is valid, and the second request's last message has `role: "tool"` and contains `"rejected"` and `"name"`.
  - `repairs after a provider invalid_output`: first `{error:{code:"invalid_output", retryable:true}}` (`times: 1`), then a good call. The result is valid, after 2 requests.
  - `gives up after the configured repairs`: an always-bad call with `repairs: 2`. It rejects with `code === "invalid_output"` and `retryable === false`, and `fake.calls("worldGen").length === 3`. The helper passes router `retries: 0`, so the router adds no attempts.
  - `rethrows non-output errors`: `{error:{code:"auth"}}` rejects with `code === "auth"` after a single helper attempt.
